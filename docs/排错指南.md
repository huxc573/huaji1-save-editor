# 排错指南

分两部分：**玩家遇到的问题**（先看各自的解决办法），**开发者定位游戏报错**。

---

## 一、玩家速查表

| 现象 | 原因 | 解决 |
|---|---|---|
| 保存失败 / 提示文件被占用 | 游戏还开着 | 退出游戏再保存 |
| 提示"找不到 TP.dll" | 缺游戏自带的依赖 | 把游戏根目录（有 `Game.exe` 那层）的 `TP.dll`、`Socket.dll` 复制到程序旁边 |
| 读档提示"存档的主人不是你" | 换了电脑，`$存档id` 与本机机器码不符 | 「机器码」页 →【填入本机机器码】→ 保存 |
| 金钱改完进游戏变成 0 / 游戏卡死 | 只改了 `@cash` 的一部分 | 用界面上的「金钱」框改（会自动重算 LockNumber 的 6 组），不要直接改树里的值 |
| 游戏里打开**召唤兽**界面弹 `NoMethodError: undefined method '[]' for nil:NilClass` | 召唤兽的 `@name` 被改成了 `$pet` 名字表外的名字 | 「角色 / 召唤兽」页 →【一键修复名字】 |
| 游戏里点物品提示"该物品无法使用！再试也不能用，233333" | 物品实例没登记进 `$data_items`（或缺 `@quality`） | 物品栏 →【一键修复异常格】 |
| 只改了第 1 格物品，第 2 格图标也变了 / 点物品报 `cannot convert Array into String` | 旧版本（0.4 及以前）的对象链接 bug | 用 0.5+ 的版本把物品栏**再写一次**（会自动整条重写 `$data`） |
| 改完名字进游戏没变 | 改的是 `@name`，但界面显示的是 `@new_name` | 用【设为显示名(@new_name)】，或先【清除显示名】 |
| 召唤兽列表里少了几只 | 那几只是"无主"（已放生/残留） | 勾上「显示无主（已放生）的召唤兽」 |
| 技能名显示成"技能123" | 找不到游戏的 `Data/Skills.rxdata` | 把工具放到游戏目录里，或用【选择存档…】选游戏里的 `Audio\BGM\sy.ogg`（工具会向上找 `Data/`） |

## 二、开发者：定位游戏报错

RPG Maker XP 的报错长这样：

```
脚本 'Sys <召唤兽>' 的 147 行发生了 NoMethodError.
undefined method '[]' for nil:NilClass
```

### 第 1 步：把行号换算成"脚本里的行号"

游戏是加密脚本，我们手上的明文 `.rb` 是从 `Data/Scripts` 提取出来的。
**提取产物里"隔行是空行"**（原始行尾是 `\r\n`，被记成了两行），所以：

```
游戏里的行号 = 去掉空行后的行号
```

验证：某脚本原始 770 行 `\n`、1540 行 `\r`，去掉空行正好 770 行。

```powershell
$env:XJ_GAME = "D:\Games\画迹1：落日情缘"
python probes\probe_show_script.py 0163 140 155     # 打印该段落的 140~155 行
```

`probes/probe_show_script.py <文件名前缀> <起> <止>`：自动按前缀找脚本、
去掉空行、打印带**游戏行号**的片段。

### 第 2 步：找报错类型对应的坑

| 报错 | 通常是 |
|---|---|
| `undefined method '[]' for nil:NilClass` | 用某个值去索引表/数组，但那个值是 `nil`（表里没这个键 / 对象不存在） |
| `undefined method 'xxx' for nil:NilClass` | 同上，且调的是方法 |
| `cannot convert Array into String` | **对象链接错位**：本该是字符串的字段解出来是数组（见 `存档格式.md` 5.2） |
| `undefined method 'xxx' for #<RPG::Item…>` | 字段类型不对（例如把数量写成了字符串） |
| 游戏**卡死**（不是崩溃） | 大概率是 `LockNumber` 6 组不一致（金钱被手改坏） |

### 第 3 步：从报错行反推是哪个字段

`nil[...]` 这种，去那一行找 `xxx[...]`，然后**往回追 `xxx` 是怎么来的**：

```
$图表[24].bitmap.draw_text(..., $pet["#{baby.name}"][7].to_s, 0)
                          └─── 表：$pet（脚本 0011 定义，键是宠物名字）
                                └── 名字：baby.name → Game_Actor#name → @name
```

经验：`$` 开头的全局变量（`$pet`、`$data`、`$宠物装备待机动画`…）都是在某个脚本里
用字面量表定义或运行时填的，**搜它的定义位置**就能知道"合法的取值范围"。

### 第 4 步：反查存档，确认是数据问题

写个小探针，把"存档里的值"和"脚本要求的取值范围"对一遍。例如这次的
"召唤兽名字不在 `$pet` 表里"：

```powershell
python probes\probe_pet_table.py    # 列出 $pet 的键，并检查每只召唤兽的 @name 在不在表里
```

输出会直接点出「槽位 166 现在叫『二郎神』（模板 150 二郎真君）」这种可疑项。

通用套路（`probes/` 里都是这个形状的脚本）：

1. `MOD.Doc(SAVE, C.make_bridge(DLL_DIR), print)` 打开存档；
2. 遍历候选对象，收集可疑字段；
3. 和脚本里的合法集合求**差集**；
4. 差集非空 → 就是它。

## 三、开发者：工具自身的问题

| 现象 | 原因 / 解决 |
|---|---|
| `EditError: 该位置已被更大的改动覆盖，请先撤销那个改动` | 整体重写某个对象后又去改它内部的字段。改用 `PatchEngine.replace_object()`（它会把这棵子树登记成"根"，见 `docs/开发指南.md` 铁律 1） |
| 写完后游戏里读不到新值，但字节补丁确实打了 | 只改了字节没同步内存树。用 `set_array_element` / `replace_object` 这两个会同步 `items` / `ivars` 的方法 |
| 保存报"有 N 个对象链接解析不到目标" | `_check_links()` 拦下来的，说明改动破坏了链接。检查是不是漏了 `register()` 某种节点类型 |
| 界面改了但表格没变 | 回调里忘了 `fill_*()`；模型层改完值要同步内存树 |
| 打包后运行报 `No module named _tkinter` / 界面起不来 | 忘了 `--add-data` 带 tcl 库，或没设 `TCL_LIBRARY` |
| 从测试脚本启动 exe 失败（退出码 1） | 没清 `PYTHONHOME` / `PYTHONPATH` / `VIRTUAL_ENV` |
| 找不到游戏目录 | 设置 `XJ_GAME` 环境变量，或在游戏目录下运行（`src/xj_env.py`） |
| 保存时报 `MarshalError: 未知类型 't' (0x74) @数字` | **整数编码写坏了**：需要 5 字节的值被当成 Fixnum，长度字节写成 `05`（在 `w_long` 里意思是"直接值 0"），一个字节都不消耗 → 整条流错位。见下方“铁律 4” |
| 报 `序列化嵌套过深（可能有循环引用）` | 这个存档里有**真循环**（`Game_Actor#@who_attack_me` 是 `Game_Enemy`，它的 `@who_attack_me` 用 `@N` 指回这个 `Game_Actor`）。整条重写要传 `table={}`（编号模式） |
| 放弃修改之后再改物品数量，保存后发现数量是 0 | `discard()` 只丢了补丁引擎，内存树里还是旧节点（`start/end` 被打过整块区间标记）→ 把整格区间写成了一个数字。现在 `discard()` 会用原始明文重新解析 |
| 存档里 `@target_index` 之类的负数比真值小 5（-1 变成 -6） | 解析"直接小负数"时少了 `+5`。已经修了；**旧版写过的档**需要用 `tools/repair_pet_names.py` 那样的思路把值改回 -1 |

## 四、出事之后怎么救

1. **先停下**，别再往同一个存档写；
2. `sy.ogg.bak` 是工具每次保存前自动生成的备份 —— 改名回 `sy.ogg` 就能退回上一步；
3. 旧版本的目录里还有更早的备份（本项目开发时用过 `sy.ogg.init` 之类的名字）；
4. 只有**数据**坏了（例如名字、数量）通常还能救：
   * 名字 → 【一键修复名字】
   * 物品格 → 【一键修复异常格】
   * 结构与模板对不上 → 用界面里对应的"重建"操作
5. 真救不回来时，把存档 + 复现步骤发到
   [issues](https://github.com/huxc573/huaji1-save-editor/issues)，
   附上工具里【导出报告】的结果，大部分问题看报告就能定位。

## 五、写测试时的教训（血泪）

**0.4 版本曾出现"测试全绿但存档已坏"**：当时所有测试都只比较**字节**，
而对象链接错位在字节层完全看不出来（每一段都"写对了地方"，只是里面的 `@N` 指错了）。

所以本项目的测试约定：

* 比较**链接展开后**的字段值，而不是字节；
* 每次写入后都要断言"**其它顶层对象一个字节都没变**"
  （`test_pets.py` / `test_pack.py` 里那段 `before_other` 对比）；
* 保存后必须**重新解密读回**再断言一次；
* 复杂操作（改名 / 技能增删）之后，再做一次"普通字段修改"，确保不会
  因为"整体重写对象"而让后续补丁失败（这正是 v1.0 修的那个 bug）；
* **边界值要成对测**：`tests/test_marshal_fix.py` 把 `0/122/123/128/0xFFFFFFFF/2**32`
  和 `-1/-124/-129/-400/-65535/-2**31` 这类整数逐个"编码再解回来"比对 ——
  v1.1 的两个写坏档 bug（4 字节以上的整数、负数的符号字节）都是靠这个才暴露的；
* **不能只信自己的读法**：把"工具写出来的字节"和"游戏自己写的字节"对一下
  （例如拿 `!Tools\0.存档\*.save.Bak` 做基准）才能发现"读错了又写回去"的漂移；
* **整条重写功能要在有环的存档上试**（战斗过的档就有环），否则只会在
  `序列化嵌套过深` 上撞墙；
* **测试里绝不能对真实存档 `Doc(SAVE).save()`**：必须 `copy2` 一份再开。
  曾经因为这一行把玩到一半的真实存档写掉了（虽然值可以改回来，但很吓人）。
