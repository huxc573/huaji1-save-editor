# 逆向过程与工具

记一下"这些东西是怎么查出来的"，方便以后遇到别的 RMXP 游戏复用同一套方法。

> 本仓库**不包含**游戏脚本的反编译产物（那是游戏原作者的版权代码）。
> 下面的方法指的是"如何在你自己的机器上做分析"，工具也只依赖你自己提取的结果。

---

## 1. 思路总览

```
1. 找存档            → 从 Save_Load 脚本里翻 $save_path
2. 拆容器            → 魔数 / 长度 / zlib
3. 调加解密          → 找出游戏自带的 DLL 与导出函数、口令
4. 解明文            → 逐个 Marshal 对象解析，做字节区间标注
5. 读懂语义          → 把脚本明文提取出来，搜"这个字段被谁读/写"
6. 探针验证          → 用 Python 直接开存档，把"存档里的值"和"脚本要求的取值范围"对差集
7. 改 → 读回校验     → 只打差分补丁 + 保存后重新解密比对
```

关键经验：**每次都要用脚本原文去"证实"，不要猜。**
本项目的每一个结论（`@babys` 顺序、放生不删对象、`$pet` 键是名字……）
都能指到具体脚本的具体行。

---

## 2. 拆容器

```python
import zlib, struct
blob = open('sy.ogg', 'rb').read()
assert blob[:4] == b'\x0D\x0F\x3E\x03'          # 魔数
declared = struct.unpack('<I', blob[4:8])[0]    # 声明的密文长度
cipher = zlib.decompress(blob[8:])              # 密文
assert len(cipher) == declared                  # 自校验
```

**不要**自己把 zlib 解好再喂给 `TP.dll` —— 它的 `DS1`/`DS2` 自己处理整个容器。

## 3. 找加解密接口

* 游戏目录里一堆 `*.dll`，其中 `TP.dll` 体积明显（约 680 KB）；
* 用 `dumpbin /exports`（VS 自带）或 Python 的 `pefile` 看导出表 → 找到 `DS1` / `DS2`；
* 口令之类的小字符串可以直接在 DLL/脚本里搜（本作是 `"xjy.11"`，写在脚本里）；
* 调用方式：stdcall、2 个参数（文件路径、口令）、**原地改文件**。
* 64 位进程调不了 32 位 DLL → 用 `csc /platform:x86` 编一个宿主中转
  （源码见 `src/XJCodec32.cs`，这也是 `XJCodec32.exe` 的来历）。

穷举加密算法没有成功（见 `probes/crack_bf.py`、`probes/probe_cipher.py`），
所以**永远走 DLL**。

## 4. 解析 Marshal

标准 Ruby Marshal 4.8，但**整数编码是非标准变体**（+5 偏移，见
[`存档格式.md`](存档格式.md) 5.1）。解析器要解决的核心问题是
**每个节点记住自己在明文里的字节区间** —— 这是后面"只打差分补丁"的基础。

解析产物：

```
[{'head': ..., 'node': <节点>, 'links': [...]}, ...]   # 19 个顶层对象
```

## 5. 把游戏脚本变成可读文本

脚本是加密的 `Data/Scripts`（本作用 `Game.dll` + `TRGSSX.dll` 保护）。
我们当时的做法是先把它解出来、按段导出成一个个 `.rb` 文件，放在
`<游戏目录>/Try/scripts/`：

```
0000_xxx.rb   0001_xxx.rb   ...   0191_xxx.rb
_all_scripts.rb           ← 全部段落拼在一起（带 @@SCRIPT 编号标记）
```

⚠️ 提取产物有个坑：**文件里"隔行是空行"**
（原始行尾 `\r\n` 被记录成了两行），所以

```
游戏里的行号 = 去掉空行后的行号
```

`probes/probe_show_script.py` 就负责"去掉空行 + 打印带游戏行号的行"。

## 6. 在脚本里搜什么

`probes/probe_pet_order.py` 是这类脚本的模板：

```powershell
python probes\probe_pet_order.py 放生 @babys Window_Baby 宠物 召唤兽
```

它会按关键词扫全部脚本，按文件聚合打印命中行（**行号已经是游戏行号**）。

常用套路：

| 想查什么 | 搜什么 |
|---|---|
| 某个变量/字段被谁用 | `@成长`、`@babys`、`$pet` |
| 某个功能在哪实现 | 界面上的中文按钮名（`放生`、`改名`、`参战`） |
| 报错行对应什么 | 脚本名 + 报错行号（先做行号换算） |
| 某个数据从哪来 | `load_data`、`Data/` 文件名 |

## 7. 写探针（`probes/` 里的脚本）

统一形状：

```python
import os, sys
HERE = os.path.dirname(os.path.abspath(__file__))
sys.path.insert(0, os.path.join(os.path.dirname(HERE), 'src'))
from xj_env import game_dir as _game_dir
GAME = _game_dir()
import xj_codec as C, xj_marshal as M, xj_model as MOD

doc = MOD.Doc(os.path.join(GAME, 'Audio', 'BGM', 'sy.ogg'),
              C.make_bridge(GAME), print)
for r in doc.actors_pet(include_unowned=True):
    print(r['id'], r['name'], r['tpl'])
```

`probes/` 里现有的脚本：

| 脚本 | 用途 |
|---|---|
| `probe_show_script.py` | 打印某个脚本段落的指定行（去空行 = 游戏行号） |
| `probe_pet_order.py` | 按关键词扫全部脚本 |
| `probe_pet_state.py` | 导出召唤兽槽位 / `@babys` / `@name` 现场快照 |
| `probe_pet_map.py` | 打印 `@原id` / `@现id` / `@编号` 映射，比对两份副本 |
| `probe_pet_table.py` | 解析 `$pet` 表并检查每只召唤兽的名字是否合法 |
| `probe_item_fields.py` | 对比"物品模板 vs 实例"的字段差异（发现 `@standard`/`@quality`） |
| `probe_cipher.py` / `crack_bf.py` | 加密算法穷举（历史记录，结论是"不匹配"） |
| `analyze_pack.py` / `pack_analyze.txt` | 原档 vs 现档的**逐格对象编号对比**（发现链接错位的关键） |
| `analyze_containers.py` | 三个物品容器的结构统计 |

## 8. 从"能读"到"能写"

写入引擎的三条设计原则（细节见 [`开发指南.md`](开发指南.md) 铁律 1）：

1. **能只改一个字段就不要动一整块** —— 解析时记下字节区间，改动时只重编码那个区间；
2. **要动一整块就必须整条重写，并把 `@N` 全部展开** ——
   自包含序列化（`M.serialize`）保证编号自洽；
3. **写回前体检、写回后读回校验** —— `_check_links()` + `save_plain()`。

`probes/analyze_pack.py` 那个"逐格对象编号对比"的表，就是当年发现
"链接错位"的输出，值得一看（`pack_analyze.txt`）。

## 9. 一般化的经验

* **字节正确 ≠ 语义正确**：对象链接、编号偏移这类问题在字节层看不出来，
  测试必须比较"链接展开后的值"。
* **把"游戏侧的校验"当成规格**：`item_can_use?`、`$pet[名字][7]`、
  `learn_skill` 的排序……工具必须和游戏**完全一致**，而不是"看起来对"。
* **善用差集**：把存档里的值和脚本里的合法集合求差集，能一眼看出坏在哪一条。
* **每次结论都记下"证据"**（脚本编号 + 行号 + 代码），
  否则过几天就不记得为什么这么写了 —— 本项目所有关键注释都带证据。
